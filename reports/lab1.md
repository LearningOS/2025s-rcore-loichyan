# rCore 教程第 3 章实验报告

## 成果简述

通过一个全局的 `BTreeMap` 记录了每个任务的的系统调用历史信息，实现相当直白简陋，仅适用于单线程．

## 简答

### 非法程序的报错

部分输出如下：

```console
[rustsbi] RustSBI version 0.3.0-alpha.2, adapting to RISC-V SBI v1.0.0
...
[kernel] PageFault in application, bad addr = 0x0, bad instruction = 0x804003a4, kernel killed it.
[kernel] IllegalInstruction in application, kernel killed it.
[kernel] IllegalInstruction in application, kernel killed it.
```

分别对应于：

1. _ch2b_bad_address_: 访问了非法地址 `0x0`
2. _ch2b_bad_instructions_: 执行 S 特权级指令 `sret`
3. _ch2b_bad_register_: 访问 S 特权级寄存器 `sstatus`

对于*第 1 点*，我还发现在内核中访问非法地址，比如 _0x80001000_（被 rustsbi 设置为固件地址）会导致程序直接卡死，通过 GDB 调试猜测应该是由于 rustsbi 没能正确处理异常，导致程序永远卡在出错的指令上；同样的情况发生在用户态会被内核捕捉．

### 陷入处理代码

1. 刚进入 `__restore` 时，`sp` 指向任务的 TrapContext．`__restore` 可用于启动用户程序以及恢复用户程序的执行状态．
2. 写入 `sstatus`，主要是设置 `SPP` 字段，使得 `sret` 返回后特权级改为 U 模式；写入 `sepc`，这是用户陷入发生时的指令位置，使得 `sret` 返回后用户程序能继续运行；写入 `sscratch`，这里保存了内核栈的位置，使得用户系统调用或发生异常时，内核能够正确运行．
3. `x2` 是 `sp`，必须最后恢复，否则会导致 TrapContext 的指针丢失；`x4` 时 `tp`，目前的实现中此寄存器没有用到．
4. 此指令用户交换当前任务的用户栈和内核栈，执行后 `sp` 和 `sscratch` 分别指向内核栈和用户栈．
5. `sret`，原因如 `(2)` 所述．
6. 执行后 `sp` 和 `sscratch` 分别指向用户栈和内核栈．
7. `ecall` 或者任意一条引发异常的指令．
